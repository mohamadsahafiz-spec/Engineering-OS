## Purpose

This document serves as the Engineering-OS decision guide for Cloudflare D1.

It focuses on engineering decisions, architectural considerations, operational best practices, and lessons learned from real-world projects.

The objective is to determine when D1 is the appropriate database solution and how it should be integrated into Cloudflare-based applications.

---

# Overview

Cloudflare D1 is a serverless SQL database built on SQLite and tightly integrated with Cloudflare Workers.

It is designed for lightweight relational data storage with global deployment and minimal operational overhead.

Within Engineering-OS, D1 serves as the primary relational database for Cloudflare-native applications.

---

# Primary Responsibilities

Cloudflare D1 should be responsible for:

- Relational data storage
- SQL queries
- User records
- Configuration data
- Application metadata
- Structured operational data
- Transactional records

Business logic should remain inside Workers.

D1 should remain responsible only for data persistence.

---

# When to Use

Use D1 when:

✓ Structured relational data is required

✓ SQL queries are preferred

✓ Tight integration with Workers is desired

✓ Operational simplicity is important

✓ Lightweight applications are being developed

---

# When NOT to Use

Avoid D1 when:

✗ Large-scale analytical workloads

✗ Extremely high write throughput

✗ Heavy transactional enterprise systems

✗ Multi-terabyte databases

✗ Existing enterprise database infrastructure already satisfies requirements

Always choose the database according to workload rather than popularity.

---

# Best Practices

- Design normalized schemas.
- Use parameterized SQL queries.
- Validate all user input.
- Keep business logic inside Workers.
- Version database migrations.
- Backup critical data regularly.
- Document schema changes.

---

# Common Mistakes

- Mixing business logic into SQL.
- Building excessively large tables without indexing.
- Ignoring schema versioning.
- Executing unnecessary database queries.
- Skipping migration testing.

---

# Lessons Learned

## Lesson 001

Workers execute application logic.

D1 stores application data.

Maintain clear separation of responsibilities.

---

## Lesson 002

Database schema changes should always be version-controlled.

Never modify production schemas without documented migrations.

---

## Lesson 003

Application failures should first determine whether the issue originates from:

- Worker
- D1
- Frontend

Isolate components before debugging.
